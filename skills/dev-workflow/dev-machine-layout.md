# Development Machine Layout

Use these conventions to recognize the storage layout of an existing workstation or cluster node and to set up a new computer when requested.

## 1. Home-level directories

The home directory provides stable entry points for code and data. These entries may be physical directories or symlinks to storage elsewhere on the machine, an HDD, or a NAS.

| Path | Purpose |
| --- | --- |
| `~/Data` | Project log folders stored directly as `~/Data/<project>_logs`. |
| `~/Datasets` | Shared datasets downloaded from public sources or generated by projects. |
| `~/Projects` | Default location for project code and configurations under development. |
| `~/workspace` | An existing workspace location that may also be present; no specific internal layout is prescribed here. |

Cross-computer synchronization software may provide an additional, personalized directory containing project code. Code outside `~/Projects` is acceptable; do not relocate it solely to match this convention.

## 2. Project logs: `~/Data`

- Store only project log folders directly under `~/Data`, using names such as `my-project_logs`. Do not add a containing project directory.
- Each log folder holds the project's generated training, deployment, and testing outputs. These files are generally not intended for direct publication.
- `~/Data` may be a physical directory or a symlink to a larger storage location.
- Project log directories must be symlinks to the appropriate directories under `~/Data`.
- Link through the stable `~/Data` entry point rather than directly to its machine-specific backing storage path.

The name and location of a log directory within a repository follow that project's existing conventions.

## 3. Shared datasets: `~/Datasets`

- Store datasets shared across projects here, including public downloads and intermediate datasets generated by projects.
- `~/Datasets` may be a physical directory or a symlink to a larger storage location.
- When projects link to shared datasets, use the stable `~/Datasets` entry point rather than its machine-specific backing storage path.
- Retain the original compressed files alongside the extracted data so that archives can be copied to an external drive for backup.

### Datasets distributed across multiple archives

Create a dataset-named directory containing all original archive parts and the extracted data. Preserve the dataset's original extracted directory names.

For example:

```text
~/Datasets/
└── TRUEMANS/
    ├── <original archive part 1>.zip
    ├── <original archive part 2>.zip
    └── Data_release/
```

### Datasets distributed as a single archive

Keep the archive directly under `~/Datasets`. Place its extracted contents in a neighboring directory with the same base name, excluding the archive suffix, such as `.zip` or `.tar.gz`.

```text
~/Datasets/
├── example-dataset.zip
└── example-dataset/
```

This arrangement supports backing up either a single archive or a dataset-named directory containing multiple archive parts.

## 4. Project code: `~/Projects`

- Give each project a dedicated directory containing its code, configurations, and required repository checkouts.
- Follow each repository's existing convention for locating logs, but make every log directory a symlink into `~/Data`.
- Two projects may use separate checkouts of the same repository on different branches and intentionally link to the same log directory under `~/Data`.
- Projects in other locations, including synchronized directories, follow the same data-linking convention. Their location alone is not a layout error.

The dependency direction is from project directories to shared data locations. Shared data should not depend on a particular repository checkout to remain accessible.

## 5. Portable symlinks

In this document, `~` is shorthand for the current user's home directory. A filesystem symlink does **not** expand a literal `~` stored in its target.

To avoid embedding usernames or machine-specific storage paths:

- Store a relative target calculated from the directory containing the symlink.
- Point that target through the home-level `Data` or `Datasets` entry point.
- Do not resolve those entry points to their backing storage paths when constructing the target.
- Recalculate the relative target for projects at different directory depths.

For example, the link at `~/Projects/my-project/logs` can store the target `../../Data/my-project_logs`. It then reaches `~/Data/my-project_logs` without embedding a username or the physical storage mount path.

Relative links depend on the directory layout. Check them again when moving a project; they are not automatically portable across different folder structures.

## 6. Recognizing an existing machine

1. Inspect the home-level entry points and identify which are physical directories or symlinks.
2. Identify the backing storage for `~/Data` and `~/Datasets` and the existing project locations, including synchronized folders.
3. Inspect project log and dataset links against the conventions above.
4. Report any differences that matter to the requested task. Recognizing the layout does not itself require moving files or replacing links.

## 7. Setting up a new machine

When asked to set up a machine:

1. Identify the intended storage locations for generated data, shared datasets, and project code. Ask for any storage choices that are not specified or evident from the machine's existing configuration.
2. Create the home-level entry points as physical directories or symlinks to the chosen storage locations.
3. Create project directories and organize datasets using the conventions above.
4. Create the required data directories and relative project links through `~/Data` or `~/Datasets`.
5. Verify that the links resolve to the intended locations and that those locations are accessible for the task.

Preserve existing files and intentional project locations when applying this layout.
